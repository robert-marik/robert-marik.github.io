Praktický přehled práce s SSH od vytvoření klíče přes konfiguraci klienta
a zabezpečení serveru až po diagnostiku. Návod předpokládá OpenSSH (Linux,
macOS, Windows 10/11). Zástupné hodnoty (`uzivatel`, `server.example.com`,
`nazev`) nahraďte vlastními.

## 1. Generování nového SSH klíče

Používejte moderní algoritmus `ed25519` a klíč pojmenujte podle jeho
účelu, ne výchozím univerzálním názvem.

```bash
ssh-keygen -t ed25519 -C "vas.email@example.com" -f ~/.ssh/id_ed25519_nazev
```

Vzniknou dva soubory: tajný klíč `id_ed25519_nazev` a veřejný klíč
`id_ed25519_nazev.pub`.

| Situace | Co udělat |
| --- | --- |
| Klíč pro ruční práci | Zadejte **silnou passphrase**. Pokud klíč někdo zcizí z disku, bez passphrase ho nepoužije. |
| Klíč pro automatizaci (cron, skripty) | Vygenerujte ho bez passphrase parametrem `-N ""` a omezte jeho použití (viz oddíl 9). |

> **Tip:** Přepínač `-C` je jen komentář (popisek klíče). Neovlivňuje
> bezpečnost, pouze usnadňuje orientaci.

## 2. Zkopírování klíče na server

Veřejný klíč se uloží do souboru `~/.ssh/authorized_keys` na serveru:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_nazev.pub uzivatel@server.example.com
```

Pokud přihlášení klíčem nefunguje, zkontrolujte na serveru práva:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

> **Pozor:** Domovský adresář uživatele na serveru nesmí být zapisovatelný
> pro skupinu ani ostatní, jinak SSH server klíč ignoruje.

## 3. Konfigurace SSH klienta (`~/.ssh/config`)

Pokud nepoužíváte výchozí názvy klíčů, klient neví, který klíč použít pro
kterou službu. Vytvořte (nebo upravte) soubor `~/.ssh/config` na svém
počítači:

```text
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/id_ed25519_github
  IdentitiesOnly yes

Host skola
  HostName server.example.com
  User vas_login
  IdentityFile ~/.ssh/id_ed25519_skola
  IdentitiesOnly yes
```

Pak se stačí připojit zkráceně: `ssh skola`.

| Volba | Význam |
| --- | --- |
| `Host` | Zkratka (alias), kterou píšete do příkazu `ssh` |
| `HostName` | Skutečná adresa serveru |
| `User` | Přihlašovací jméno |
| `IdentityFile` | Cesta k tajnému klíči |
| `IdentitiesOnly yes` | Použije se jen zde uvedený klíč, ne všechny klíče z agenta |
| `Port` | Port serveru, pokud není výchozí 22 |

Soubor má mít práva `chmod 600 ~/.ssh/config`.

> **Pozor:** SSH čte `config` shora dolů a pro každou volbu platí **první
> nalezená hodnota**. Konkrétní bloky proto patří nahoru, obecný blok
> `Host *` s výchozími hodnotami na konec souboru.

## 4. Správa passphrase pomocí `ssh-agent`

Pokud klíč chráníte passphrase, nechcete ji psát při každém připojení.
Tuto práci převezme `ssh-agent`.

**1) Ověřte, zda agent běží:**

```bash
ssh-add -l
```

Výpis „The agent has no identities“ znamená, že agent běží, ale je
prázdný. Chyba „Could not open a connection to your authentication agent“
znamená, že neběží.

**2) Spusťte agenta (pokud neběží):**

```bash
eval "$(ssh-agent -s)"
```

**3) Přidejte klíč do agenta:**

```bash
ssh-add ~/.ssh/id_ed25519_nazev
```

**4) Volitelně: přidávejte klíče do agenta automaticky** při prvním
použití. Na **konec** `~/.ssh/config` přidejte:

```text
Host *
  AddKeysToAgent yes
```

> **Tip:** Na Linuxu s desktopem GNOME běží agent obvykle automaticky
> (GNOME Keyring nebo `gcr-ssh-agent`) a passphrase si může zapamatovat
> po přihlášení do desktopu. Konkrétní chování se mezi distribucemi
> mírně liší.

## 5. Údržba klíčů

| Úkol | Příkaz |
| --- | --- |
| Změnit nebo přidat passphrase | `ssh-keygen -p -f ~/.ssh/id_ed25519_nazev` |
| Obnovit veřejný klíč z tajného | `ssh-keygen -y -f ~/.ssh/id_ed25519_nazev > ~/.ssh/id_ed25519_nazev.pub` |
| Zobrazit otisk (fingerprint) klíče | `ssh-keygen -l -f ~/.ssh/id_ed25519_nazev.pub` |
| Odebrat klíč z agenta | `ssh-add -d ~/.ssh/id_ed25519_nazev` |
| Odebrat všechny klíče z agenta | `ssh-add -D` |

> **Rotace a odvolání:** Při podezření na únik nebo při vyřazení zařízení
> smažte příslušný řádek z `~/.ssh/authorized_keys` na všech serverech,
> odeberte veřejný klíč z GitHubu/GitLabu a vygenerujte nový pár.

## 6. Přidání klíče na GitHub / GitLab

1. Zobrazte veřejný klíč: `cat ~/.ssh/id_ed25519_github.pub`
2. V nastavení účtu otevřete **SSH and GPG keys → New SSH key** (GitLab:
   **Preferences → SSH Keys**) a vložte celý řádek.
3. Ověřte spojení: `ssh -T git@github.com`

## 7. Zabezpečení serveru (`/etc/ssh/sshd_config`)

Až budete mít přihlášení klíčem ověřené, vypněte přihlašování heslem:

```text
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
```

Konfiguraci otestujte a načtěte:

```bash
sudo sshd -t                       # kontrola syntaxe, bez výpisu = v pořádku
sudo systemctl reload ssh          # Debian/Ubuntu; jinde služba sshd
sudo sshd -T | grep -i passwordauthentication   # skutečně platná hodnota
```

> **Pozor:** Soubory v `/etc/ssh/sshd_config.d/*.conf` se načítají na
> začátku hlavního konfiguračního souboru a i zde platí první nalezená
> hodnota. Například `50-cloud-init.conf` na cloudových serverech
> s `PasswordAuthentication yes` vaše nastavení přebije. Upravte proto
> i tyto soubory, nebo vlastní nastavení vložte do souboru s nižším
> číslem, např. `/etc/ssh/sshd_config.d/10-zabezpeceni.conf`.

> **Pozor:** Nejdříve vyzkoušejte přihlášení klíčem v **druhém terminálu**
> a teprve pak vypněte hesla. Stávající relaci nechte otevřenou, dokud
> změnu neověříte, jinak se můžete zamknout.

Proti opakovaným pokusům o přihlášení pomůže [fail2ban](/navody/fail2ban).

## 8. Skok přes jiný server (bastion / ProxyJump)

Když je cílový server dostupný jen přes mezilehlý stroj, použijte
`ProxyJump`. Je bezpečnější než přeposílání agenta.

```text
Host vnitrni-server
  HostName 10.0.0.15
  User uzivatel
  ProxyJump uzivatel@bastion.example.com
  IdentityFile ~/.ssh/id_ed25519_prace
  IdentitiesOnly yes
```

Nebo jednorázově: `ssh -J uzivatel@bastion.example.com uzivatel@10.0.0.15`

> **Pozor:** Přeposílání agenta (`ForwardAgent yes` / `ssh -A`) zapínejte
> jen u serverů, kterým plně důvěřujete. Správce cizího serveru by mohl
> váš agent zneužít.

## 9. Volby v `authorized_keys` (omezení klíče)

Každý řádek v `~/.ssh/authorized_keys` je jeden povolený klíč. Volby se
píší **před** typ klíče, oddělují se čárkou a **bez mezer** (mezery smí
být jen uvnitř uvozovek):

```text
volba1,volba2="hodnota" ssh-ed25519 AAAAC3Nza... komentar
```

Bez voleb má klíč plná práva uživatele. Pro automatizaci je to zbytečně
mnoho.

| Volba | Co dělá |
| --- | --- |
| `from="seznam"` | Klíč funguje jen z uvedených IP adres, rozsahů CIDR nebo jmen počítačů. Povoluje hvězdičky, vykřičník (`!`) vyloučí výjimku. |
| `command="příkaz"` | Ať klient zadá cokoli, spustí se jen tento příkaz. Původní požadavek je v proměnné `SSH_ORIGINAL_COMMAND`. |
| `restrict` | Vypne vše naráz: přesměrování portů, agenta, X11, pty i `~/.ssh/rc`. Doporučuje se uvádět vždy (OpenSSH 7.2+). |
| `no-port-forwarding` | Zakáže tunelování portů. |
| `no-agent-forwarding` | Zakáže přeposílání agenta. |
| `no-X11-forwarding` | Zakáže grafické aplikace přes SSH. |
| `no-pty` | Zakáže interaktivní terminál. |
| `port-forwarding`, `pty` | Po `restrict` znovu povolí jednotlivou vlastnost. |
| `permitopen="host:port"` | Omezí, kam smí klíč tunelovat (při povoleném přesměrování portů). |
| `expiry-time="20271231"` | Po uvedeném datu klíč přestane platit (OpenSSH 8.2+). |
| `cert-authority` | Klíč na řádku je certifikační autorita, ne běžný uživatel (SSH certifikáty, pokročilé téma). |

**Příklady:**

```text
# Záloha z jednoho serveru, jen čtení jedné složky
restrict,from="203.0.113.10",command="/usr/bin/rrsync -ro /srv/data" ssh-ed25519 AAAA... zaloha-cron

# Klíč, který umí jen restartovat jednu službu
restrict,from="192.168.1.20",command="sudo systemctl restart myapp" ssh-ed25519 AAAA... restart-myapp

# Přístup jen k databázi přes tunel
restrict,port-forwarding,permitopen="10.0.0.5:5432" ssh-ed25519 AAAA... db-tunel

# Dočasný přístup, který sám vyprší
restrict,pty,expiry-time="20271231" ssh-ed25519 AAAA... kolega-externista
```

> **Na co si dát pozor:**
>
> - U `from=` může dynamická IP adresa nebo NAT odmítnout i vás.
>   Skutečnou zdrojovou adresu zjistíte na serveru příkazem `echo $SSH_CLIENT`.
> - `SSH_ORIGINAL_COMMAND` je nedůvěryhodný vstup. Vždy ho validujte
>   a nikdy ho nespouštějte přes `eval`.
> - Příkaz se `sudo` vyžaduje pravidlo v sudoers bez hesla omezené
>   přesně na tento příkaz (`sudo visudo -f /etc/sudoers.d/myapp`).
> - Skript `rrsync` je součástí balíčku rsync (od verze 3.2.4 jako
>   `/usr/bin/rrsync`, ve starších verzích v `/usr/share/doc/rsync/scripts/`).
> - Vnitřní uvozovky v hodnotě escapujte (`\"`).
> - Po úpravě otestujte přihlášení z **nové** relace a stávající nechte otevřenou.
> - Podpora voleb závisí na verzi OpenSSH. Přesnou syntaxi najdete
>   v `man sshd` (sekce AUTHORIZED_KEYS FILE FORMAT).

## 10. Jeden klíč pro více serverů

Cíl: připojovat se na více serverů jedním klíčem, a to jak krátkým
názvem (`ssh um`), tak plným (`ssh um.mendelu.cz`). Servery z příkladu:

- MENDELU: `um`, `math4u`, `jupyter` (plné názvy `*.mendelu.cz`)
- VŠB: `math4u-latex.vsb.cz`, `msr-latex.vsb.cz`

```text
# --- Krátké aliasy (doplní plný název serveru) ---
Host um
  HostName um.mendelu.cz

Host math4u
  HostName math4u.mendelu.cz

Host jupyter
  HostName jupyter.mendelu.cz

Host math4u-latex
  HostName math4u-latex.vsb.cz

Host msr-latex
  HostName msr-latex.vsb.cz

# --- Společné nastavení pro MENDELU ---
Host um math4u jupyter *.mendelu.cz
  User vas_login
  IdentityFile ~/.ssh/id_ed25519_skola
  IdentitiesOnly yes

```

**Jak to funguje:**

- SSH prochází všechny bloky, jejichž `Host` odpovídá zadanému jménu,
  a pro každou volbu použije **první nalezenou hodnotu**. Alias tak
  převezme `HostName` ze svého bloku a `User` a `IdentityFile` ze
  společného bloku.
- `Host` přijímá více vzorů najednou, oddělených mezerou. Pokrývá tak
  krátký i plný název.
- Zástupný znak `*.mendelu.cz` pokryje všechny servery v doméně, i ty,
  které přidáte později.
- `User` je rozdělený do dvou bloků, protože instituce mají obvykle
  různá přihlašovací jména. Pokud je máte stejná, spojte bloky do jednoho.

**Použití:**

```bash
ssh um
ssh jupyter.mendelu.cz
ssh math4u
```

**Nasazení veřejného klíče na všechny servery** (po jednom, přihlásíte se heslem):

```bash
for s in um math4u jupyter math4u-latex msr-latex; do
  ssh-copy-id -i ~/.ssh/id_ed25519_skola.pub "$s"
done
```

`ssh-copy-id` použije `User` i `HostName` z configu, takže stačí alias.

> **Jeden klíč, nebo dva?** Pro obě instituce můžete použít jeden klíč,
> pokud jde o stejný účel i stejného majitele. Pokud chcete oddělit
> rizika (únik klíče nezasáhne obě instituce), vytvořte
> `id_ed25519_mendelu` a `id_ed25519_vsb` a v každém bloku uveďte jiný
> `IdentityFile`.

## 11. Diagnostika a užitečné testy

**Přihlášení s konkrétním klíčem v podrobném režimu** (ukáže, které klíče
se zkoušejí a kde přihlášení selhává):

```bash
ssh -v -i ~/.ssh/id_ed25519_nazev uzivatel@server.example.com
```

Více `v` (`-vv`, `-vvv`) znamená podrobnější výpis.

**Vynucení přihlášení heslem** (test, zda server heslo povoluje):

```bash
ssh -o PubkeyAuthentication=no uzivatel@server.example.com
```

**Výpis výsledné konfigurace klienta pro daný alias:**

```bash
ssh -G skola | grep -Ei '^(hostname|user|identityfile|port) '
```

**Test GitHubu:**

```bash
ssh -T git@github.com
```

## 12. Řešení častých chyb

| Chyba | Příčina a řešení |
| --- | --- |
| `Permission denied (publickey)` | Server klíč nepřijal. Zkontrolujte `authorized_keys`, práva (`700`/`600`) a spusťte `ssh -v`. Na serveru pomůže `sudo journalctl -u ssh`. |
| `WARNING: UNPROTECTED PRIVATE KEY FILE!` | Tajný klíč má příliš volná práva. Spusťte `chmod 600 ~/.ssh/id_ed25519_nazev`. |
| `Too many authentication failures` | Agent nabízí příliš mnoho klíčů. Použijte `IdentitiesOnly yes` a `IdentityFile` v configu. |
| `REMOTE HOST IDENTIFICATION HAS CHANGED!` | Změnil se otisk serveru (přeinstalace, nebo útok). Pokud jste si jisti, že jde o legitimní změnu, odstraňte starý záznam: `ssh-keygen -R server.example.com`. |
| `Host key verification failed` | Záznam v `~/.ssh/known_hosts` nesouhlasí nebo chybí a nelze se zeptat. Postup je stejný jako u předchozí chyby. |

> **Tip:** Při prvním připojení SSH zobrazí otisk serveru. U důležitého
> serveru ho před potvrzením `yes` porovnejte s údajem od správce.

## 13. Zálohování klíčů

- Tajné klíče zálohujte **pouze šifrovaně** (správce hesel, šifrovaný
  disk nebo kontejner).
- Klíč chráněný passphrase je při záloze bezpečnější, passphrase si
  uložte zvlášť.
- Klíče, které snadno nahradíte, nemusíte zálohovat vůbec. Při ztrátě
  vygenerujte nový.
- Zvažte hardwarový klíč (YubiKey apod., `ssh-keygen -t ed25519-sk`).
  Tajná část pak neopustí zařízení.

## 14. Zlatá pravidla bezpečnosti

1. **Jeden účel = jeden klíč.** Nemíchejte osobní klíč pro GitHub,
   firemní server a školní počítač.
2. **Tajný klíč** (soubor bez přípony `.pub`) nikdy nikomu nedávejte
   a nezálohujte ho na nezabezpečená místa. Veřejný klíč (`.pub`) sdílet
   můžete.
3. **Automatizace:** Pro cron a skripty používejte výhradně dedikovaný
   klíč bez passphrase, omezený na danou úlohu a server (volby `restrict`,
   `from="…"` a `command="…"` v `authorized_keys`).
4. **Práva souborů:** Tajné klíče mají mít `chmod 600`, adresář `~/.ssh`
   `chmod 700`.
5. **Na serveru** po ověření klíčů vypněte přihlašování heslem a rootem.
